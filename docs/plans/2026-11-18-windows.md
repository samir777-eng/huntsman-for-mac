# v0.4.0: Windows build (2026-11-18)

## Problem
A friend on Windows wants the app. Razer Synapse supports the Huntsman V3 Pro on Windows, but this app is lighter,
needs no account, and has Studio. Owner chose: full feature parity in one release, no Windows tester available,
Windows treated as untested (gated).

## Research (2026-11-18; easyrazer source, cited in the research notes)
- Control: hidapi feature reports on interface 3 (MI_03), 91-byte buffer = report ID 00 + 90-byte packet; normal
  Windows driver, no driver swap. Reply readable right after SET_REPORT; retry on busy (15 ms, 10 tries).
- Depth stream: MI_01 collection col07 (V3, report 0B) / col06 (V2 Analog, report 07) via hidapi read. The 02A6's
  col07 is unconfirmed on hardware by anyone.
- Typing reactions: Raw Input (RIDEV_INPUTSINK) filtered by device name VID_1532&PID_xxxx; scancode → page-7 usage.
- Tray: pystray. Start at login: HKCU Run key `"<exe>" --service` (no admin). IPC: named pipe via
  multiprocessing.connection with an authkey file. Data %APPDATA%\Huntsman for Mac, logs %LOCALAPPDATA%.
  Sleep/lock: WTSRegisterSessionNotification / WM_POWERBROADCAST. Locks: named mutex / msvcrt.locking.
- pywebview EdgeChromium (WebView2 runtime; built into Windows 11).
- Synapse holds driver mode and overwrites the live profile; two writers mix replies. Windows Dynamic Lighting
  (LampArray autonomous mode off) makes lighting commands do nothing.

## Requirements
1. Platform layer: `platform_win.py` / existing mac code behind small interfaces (transport, depth stream, key
   listener, tray/menu, autostart, IPC endpoint, data/log dirs, locks, smart-lighting OS events). mac behaviour and
   02A6 bytes unchanged (golden tests).
2. Windows = experimental platform: on Windows every model is treated as experimental (writes need the Experimental
   support switch); the key tester (driver mode) is off on Windows; the UI says "Windows support is experimental".
3. Synapse guard: if RazerAppEngine.exe (or Synapse service) is running, stay read-only and say why; Dynamic
   Lighting on → tell the user how to turn it off for this keyboard.
4. Packaging: PyInstaller one-folder, single `Huntsman for Mac.exe`? → named **Huntsman.exe** with `--service` mode,
   zipped as `Huntsman-for-Windows-<version>.zip`, built and attached to the GitHub release by a GitHub Actions
   workflow on windows-latest that also runs the test suite (mac-only tests skipped). Unsigned: README explains the
   SmartScreen prompt.
5. Docs: README/landing page Windows section (download, SmartScreen, Synapse/Dynamic Lighting notes, untested status),
   CHANGELOG, HANDOFF. Name: app stays "Huntsman for Mac" (decision), Windows build described as "Huntsman for Mac,
   Windows build".

Non-goals: code signing, an installer (MSI), Windows-on-ARM, host-side Rapid Trigger.

## Tests (first)
Fake hid device for the Windows transport (report ID framing, busy retry, reply stripping); platform selection;
gate (Windows → experimental, key tester refused); Synapse guard; Raw Input scancode map; autostart registry value
(fake winreg); named-pipe IPC round trip (runs on mac too); PyInstaller spec lists all data files (ui/, layouts/,
layout.json, keymap.json). CI runs the suite on windows-latest and macos-latest.

## Risk
Nothing is checked on a Windows PC before release. Mitigated by the gate, read-only under Synapse, typing-restore
paths kept, and clear "untested" labelling.

## W1 core (implemented 2026-11-18, branch `windows`)
- `platforms/__init__.py`: `current()` / `is_windows()` / `is_mac()` / `info()` (from `sys.platform` at each call),
  `data_dir()` / `log_dir()` / `log_path()`, locks `file_lock(path)`, `lock_fd`, `unlock_fd`, `try_lock_fd`
  (fcntl on the Mac, msvcrt.locking of byte 0 on Windows, polled because LK_LOCK gives up after 10 s).
- `platforms/win_hid.py`: `HidTransport(hid_module=None)` (same interface as `UsbTransport`), `HidApi` adapter.
  `huntsman_core.open_transport()` picks it on Windows; `Keyboard()` uses that.
- `ipc.py`: `UnixEndpoint(path)` (Mac, unchanged behaviour), `PipeEndpoint(address, key_path, family)` (Windows
  AF_PIPE `\\.\pipe\huntsman-for-mac-<user>`, authkey renewed at every service start in `data_dir/service.key`,
  handshake both ways in the client thread), `service_endpoint(data_dir)`; Server/Client/Subscription take either
  (a path still means the UNIX socket). `app.service_endpoint()`, `service.service_endpoint()`.
- Gate: on Windows every model needs the Experimental support switch and the key tester (00:04, 00:84) is never
  sent; `huntsman_core.model_info(model)` adds `platform`, `platform_experimental`, `model_status` (and reports
  status "experimental", no key tester, on Windows). `Api.model()` / `Api.info()` use it.
- `requirements-win.txt` pinned; `install.sh` copies `platforms/`.
- Tests: tests/test_platforms.py, test_hid_win.py, test_ipc_pipe.py, test_windows_gate.py (fakes only).
- HidTransport opens every interface-3 collection of the detected PID in turn and keeps the one that answers a
  00:81 firmware read (feature report 0 belongs to one collection only).
- Handshakes (both sides) are bounded by ipc.TIMEOUT; multiprocessing's own Client handshake is not used.
- Independent review (Opus): no Critical; Important fixed (handshake stall, collection choice, connect timeout).
- Known limits, to revisit in a later step: the pipe keeps CPython's default security (Everyone may open it
  read-only; mutual HMAC blocks commands, so DoS only), the name is predictable (squatting = service can't start),
  the key sits in roaming %APPDATA%; a pipe subscriber that stops reading blocks only its stream thread; closing the
  pipe Listener doesn't wake a blocked accept (daemon thread).

## W2 Windows front-end (implemented 2026-11-18, branch `windows`; nothing run on a Windows PC)
- Menu: `menubar.MenuState` is the shared model + handlers (build_menu, activate, set_state incl. `notice`);
  `StatusMenu` (Cocoa) and `platforms/win_tray.TrayMenu` (pystray, icon drawn with Pillow, click = open the app)
  both render it. A notice ("Read only: Razer Synapse is running") shows as a disabled first item.
- Start at login (`platforms/win_autostart.py`): HKCU `...\CurrentVersion\Run` value "Huntsman for Mac lighting" =
  `"<Huntsman.exe>" --service` (frozen) or `"<pythonw.exe>" "<service.py>"` (source; python.exe if no pythonw).
  Turned on when the service starts (`service.ensure_autostart`) and when the app starts the service
  (`app.start_service` → `win_autostart.start_service`: Run value, then a detached, console-less process).
  Quit leaves the value (same as the Mac: off until the next login or Studio use); `disable()` is for an uninstall.
  `app.entry()` dispatches `--service` to `service.main()`.
- Typing reactions (`platforms/win_keys.py`): Raw Input on a message-only window (`platforms/win_window.py`),
  usage 1/6, RIDEV_INPUTSINK; device names filtered by `VID_1532&PID_<active pid>`; set-1 scancodes + E0 → page-7
  usages (SCANCODES; Pause/Num Lock by virtual key; fake shifts ignored); de-duplicated like the Mac listener.
  `studio._key_listener` picks it on Windows.
- Smart lighting (`platforms/win_smart.WinAdapters`, picked by `inputs.smart.default_adapters()`): GetLastInputInfo
  idle, WM_POWERBROADCAST suspend/resume + console display off/on, WTS lock/unlock (hidden top-level window: power
  broadcasts skip message-only windows), foreground window's program name ("steam.exe") as the app-rule id.
  Running apps: visible titled windows' programs. UI says "program name" on Windows.
- Synapse guard (`platforms/win_guard.py`): RazerAppEngine.exe, Synapse 3 and 2 processes (Toolhelp snapshot,
  `tasklist` fallback without a window; a failed check counts as running). `huntsman_core.gate` raises
  `SynapseRunning` (an ExperimentalLocked, so every refusal path handles it; `app.refused` reason "synapse") on
  every write; cached 5 s, so writes come back after Synapse quits. Service: Studio stays off with the reason,
  `check_guard()` every 5 s updates the tray notice and turns Studio back on if Synapse turned it off. Window:
  `model()` adds `blocked` and `notices` on Windows; a notice box above the panes, write controls locked, model
  re-read every 5 s while blocked. Dynamic Lighting: `AmbientLightingEnabled == 1` → notice with the Settings
  path (never changed by the app).
- Depth stream: **decided not to implement** on Windows. The gate never allows driver mode there, so nothing could
  use it, and col07 on the 02A6 is unconfirmed; `DepthSession.start()` raises FeatureUnavailable on Windows.
- Signals: on Windows `install_signal_stop` uses plain SIGTERM/SIGBREAK handlers (no SIGHUP, no wakeup pipe);
  logoff/shutdown come as WM_ENDSESSION on a hidden window in the service, which stops and restores lighting.
  A windowed exe has no stdout/stderr: `platforms.redirect_output()` sends them to the log file.
- Pipe hardening: the pipe name is `huntsman-for-mac-<user>-<32 random hex>`, new at each service start, stored with
  the key as JSON in `%LOCALAPPDATA%\Huntsman for Mac\service.key` (`platforms.local_dir()`; not roaming); clients
  read both. Owner-only pipe DACL: not feasible with multiprocessing (`_winapi.CreateNamedPipe` always passes NULL
  security attributes) short of re-implementing the pipe server; the random name, user-only key file,
  FILE_FLAG_FIRST_PIPE_INSTANCE (CPython) and the mutual HMAC handshake are the mitigations. Documented in ipc.py.
- Tests: tests/test_win_tray.py, test_win_autostart.py, test_win_keys.py, test_win_smart.py, test_win_guard.py,
  test_win_service.py, test_ipc_pipe.py (hardening), test_ui_models.py (Windows notices, demo `&windows=`).
- For W3 packaging: entry point `app.entry` (one Huntsman.exe, windowed; `--service` runs the service); hidden
  imports `service`, `platforms.win_hid`, `platforms.win_tray`, `platforms.win_autostart`, `platforms.win_keys`,
  `platforms.win_smart`, `platforms.win_guard`, `platforms.win_window`, `pystray._win32`, `PIL.Image`,
  `PIL.ImageDraw`, `hid`, `webview.platforms.edgechromium`, `clr_loader`, `sounddevice`, `lighting.*`, `inputs.*`
  (all lazily imported); data files `ui/`, `layouts/`, `layout.json`, `keymap.json`. No icon asset needed for the
  tray. Name the build so `sys.frozen` is set (PyInstaller does).
